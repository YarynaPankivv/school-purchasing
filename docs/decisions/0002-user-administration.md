# 0002. Адміністрування працівників: роль admin, деактивація, особа «від імені»

- Статус: прийнято
- Дата: 2026-10-21
- AC: AC-ORG-09, AC-ORG-10, AC-ORG-12, AC-ORG-13, AC-ORG-16, AC-ORG-18, AC-ORG-21

## Контекст

Задача 3 зрізу ORG (`openspec/changes/impl-org`, `design.md` D5–D7). Адміністратор керує ролями й активністю
працівників, але систему не можна лишити без активного адміністратора; деактивований працівник не має ні входити, ні
потрапляти у вибір. supabase-js без транзакцій, server actions доступні прямим POST, Data API — прямим запитом із
живим JWT, тож правила тримає база, а застосунок лише перетворює її відмови на тексти PM.

## Рішення

- **Прямого `grant update (role, is_active)` для `authenticated` немає** (правило AGENTS.md; зауваження CodeRabbit):
  `authenticated` змінює в `profiles` лише `full_name`. Адміністратор змінює `role` і `is_active` функціями
  `public.admin_set_role` / `public.admin_set_active` (`security invoker`, `supabase.rpc`), які викликають
  `private.admin_set_role` / `private.admin_set_active` (`security definer`): вони перевіряють, що викликає активний
  admin (42501), і повертають `true`, якщо профіль знайдено. Політики `profiles_update_admin` немає.
- **Охоронець `private.guard_profile_update()`** (`before update of role, is_active on profiles`, міграція
  `20261021120000_org_users.sql`) лишається другою лінією для будь-якого шляху запису: у сеансі `authenticated` зміну
  `role`/`is_active` пропускає лише активний admin (42501); `service_role` і міграції (`auth.uid() is null`) — без
  цієї перевірки.
- **Єдиний активний admin** (AC-ORG-10, 18): після зміни має лишитись інший активний admin, інакше виняток із текстом
  PM і власним SQLSTATE `ORG01`; застосунок розпізнає його за кодом (`mapOrgDbError` → `last_admin`). Дві одночасні
  зміни серіалізує `pg_advisory_xact_lock`, а не `select … for update`: блокування рядків двох адміністраторів, що
  деактивують один одного, закінчується deadlock, а консультативне блокування — ні.
- **Роль після зняття admin — похідна** (AC-ORG-21; D3): охоронець підставляє `approver`/`requester` за
  `department_approvers`, а не те, що надіслав клієнт. Ручну зміну `requester ↔ approver`, що суперечить похідній, він
  відхиляє (22023); похідну зміну від `private.sync_role()` пропускає без перевірки прав.
- **Деактивація** (AC-ORG-12): `login()` після `signInWithPassword` читає власний профіль (`profiles_select_own` діє й для
  неактивного) і виходить із тим самим текстом, що й за невірного пароля; `requireActiveUser()` робить те саме на
  кожній сторінці й action; політики нових таблиць вимагають `is_active_user()`.
- **Особа «від імені»** (AC-ORG-16): `requests.on_behalf_of_id` + `private.can_act_on_behalf()` у `requests_insert`
  (активний працівник; не-admin — заявник того самого відділу, крім адміністраторів — AC-PUR-13); `profiles_select_colleagues` показує лише
  активних колег зі спільного відділу, тож деактивованого не прочитати й прямим запитом.
- **Чернетки** (AC-ORG-13): політика `requests_delete_draft_admin` віддає на видалення лише `status = 'draft'` заявки
  деактивованого автора (`private.is_inactive_user()`, volatile, `for share` на рядок автора), тож перевірка й видалення
  йдуть одним запитом, а паралельна активація чекає завершення видалення; action `deleteDraft` лише дає зрозумілу помилку наперед.

## Розглянуті варіанти

- Обмежити зміну `role`/`is_active` лише відсутністю grant — ні: адміністратор теж працює від `authenticated`.
- Перевіряти «останнього адміністратора» лише в server action — ні: прямий запит до Data API її обійде, а дві
  одночасні дії обійшли б перевірку «прочитати, потім записати».
- `select … for update` на рядки інших адміністраторів — ні: deadlock за взаємної деактивації.
- Бан деактивованих через Admin API — ні: потрібен секретний ключ у Vercel, а його там не тримаємо.

## Наслідки

- Простіше: усі інваріанти — в одному тригері й кількох політиках; server actions — один запит.
- Складніше: правило продубльовано в `src/lib/org/users.ts` (для вимкнених кнопок і тестів), Vitest без бази його не
  перевіряє; SQL перевіряють `db-check` і ручний прохід. Під час розробки міграції прогнано на Postgres (pglite) зі
  сценаріями AC під ролями `authenticated`.
- Відповіді PM на Q2 (`design.md` D10) змінять лише умову в тригері — новою міграцією.
