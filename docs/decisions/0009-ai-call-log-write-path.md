# 0009. Запис у ai_call_log — лише через функцію record_ai_call

- Статус: прийнято
- Дата: 2026-11-26
- AC: — (операційна вимога WS11, SLO-2: ValiaBihun/2026-quitcode-dream-team#83)

## Контекст

Частку запитів помічника без стану «недоступний» (SLO-2) рахуємо з `public.ai_call_log`. Таблиця мала колонковий
`grant insert` для `authenticated` і політику «лише свій `user_id`»: будь-який активний користувач міг через PostgREST
дописати довільну кількість рядків `unavailable` і зіпсувати метрику, на яку дивиться PM. Тексту користувача в таблиці
немає, тож це не витік, а недовіра до числа.

Server action пише від імені користувача: секрету `service_role` у Vercel немає за правилом проєкту (`AGENTS.md`,
«Секрети»), тож повністю закрити запис для користувача неможливо.

## Рішення

- Прямого `INSERT` у `ai_call_log` для `authenticated` немає (прибрано і grant, і політику).
- Запис — `public.record_ai_call(...)` (`security invoker`, обгортка для `supabase.rpc`) → `private.record_ai_call(...)`
  (`security definer`, `search_path = ''`): `user_id` лише з `auth.uid()`, лише активний користувач, формат полів — CHECK
  таблиці, ліміт 200 записів на користувача за годину.
- Тест бази `tests/db/ai-call-log.test.ts`: прямий insert падає, функція працює, ліміт спрацьовує.

## Наслідки

- Підробити частку можна лише повільно (до 200 рядків за годину з одного облікового запису), а не безмежно; для навчального
  застосунку зі школою це прийнятно.
- Повністю надійний варіант — запис із сервера під `service_role` (окрема функція Edge чи секрет на сервері): потребує
  перегляду правила про секрети; тоді функцію можна закрити для `authenticated` зовсім.
